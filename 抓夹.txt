这个错误 `sequence size exceeds remaining buffer` 是 **DDS 反序列化错误**，意思是 MATLAB 端发出的消息字节流和 Ubuntu 端的 trajectory_msgs 定义对不上。这是 MATLAB ROS 2 ↔ ROS 2 Humble 之间一个**非常常见**的兼容性问题，跟你的轨迹优化代码没关系。

## 第一步：先确认机械臂到底动了没

`ros2 topic echo` 自己解析失败 ≠ controller 没收到。先去 Gazebo 窗口看一下机械臂有没有动。如果动了，那就是 echo 工具自己的问题，可以无视报错继续做实验。

也可以换一个工具验证消息确实到达：

```bash
ros2 topic hz /arm_controller/joint_trajectory       # 只看频率，不解析内容
ros2 topic info /arm_controller/joint_trajectory -v  # 看订阅者数量与QoS
```

如果 `ros2 topic info` 显示 "Subscription count: 1+"，且 MATLAB 发送时机械臂动了，说明传输是成功的，echo 只是工具问题。

## 第二步：如果机械臂确实没动，根因有 3 个常见可能

**可能 A：未初始化字段被序列化为脏数据**

MATLAB 的 `repmat(pt_template, 1, N)` 之后，`velocities/accelerations/effort` 字段是空 `[]`，理论上应该序列化为"长度为0的序列"。但在某些版本下会出错。**显式赋零**最稳：

```matlab
for idx = 1:N_send
    i = ds_idx_send(idx);
    
    points_array(idx).positions     = double(q_actual_t(i, :));
    points_array(idx).velocities    = double(zeros(1, 6));   % ★ 显式赋值
    points_array(idx).accelerations = double(zeros(1, 6));   % ★
    points_array(idx).effort        = double(zeros(1, 6));   % ★
    
    current_time = t(i) + 0.1;
    sec_part  = floor(current_time);
    nsec_part = (current_time - sec_part) * 1e9;
    points_array(idx).time_from_start.sec     = int32(sec_part);
    points_array(idx).time_from_start.nanosec = uint32(nsec_part);
end
```

**可能 B：RMW（DDS 中间件）不一致**

MATLAB ROS 2 默认用 **Fast-DDS**，而 Ubuntu Humble 默认也是 Fast-DDS，但如果你装过 cyclonedds 并 export 过环境变量，两边就对不上了。先查 Ubuntu 端：

```bash
echo $RMW_IMPLEMENTATION
```

如果输出 `rmw_cyclonedds_cpp`，就要么把 Ubuntu 切回默认：

```bash
unset RMW_IMPLEMENTATION
# 或者
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
# 然后重启 ros2_control 和 echo 终端
```

要么在 MATLAB 这边也切到 cyclone（**MATLAB 启动前**在 shell 里 export，再启动 MATLAB）。

**可能 C：header.stamp 未设置导致控制器拒收**

JointTrajectoryController 默认会用 `header.stamp` 做时间基准。MATLAB 端没有设置过 `msg_traj.header.stamp`，它会是 (0,0)。controller 会拒掉"过时"的轨迹。在 ROS 2 中可以让它用"接收到时刻"作为起点：

```matlab
% 在 send 之前补充：
msg_traj.header.stamp.sec     = int32(0);
msg_traj.header.stamp.nanosec = uint32(0);    % 0 表示用接收时刻
msg_traj.header.frame_id      = '';            % 空字符串
```

## 第三步：最小化复现以缩小问题

如果上面都试了还不动，把 N_send 降到 2 看看：

```matlab
N_send = 2;
ds_idx_send = [1, length(t)];
```

只发起点和终点。如果 2 个点的轨迹能正常收到、机械臂能动，那 51 个点失败就是 **buffer size** 问题，可以在 Ubuntu 端设置：

```bash
export FASTRTPS_DEFAULT_PROFILES_FILE=/path/to/large_buffer_profile.xml
```

或者干脆把 MATLAB 端的下发频率提高、单次点数压缩到 20 个以下。

## 推荐操作顺序

1. 先看 Gazebo 是否动了（最快验证）
2. 若没动 → 加 `header.stamp = (0,0)` + 显式赋值 `velocities/accelerations/effort`
3. 再没动 → 对齐 `RMW_IMPLEMENTATION`
4. 还不行 → 降到 2 点测试

把每一步的结果（Gazebo 动/没动、echo 是否还报错、controller_manager 的日志）反馈给我，我们逐步收敛。
